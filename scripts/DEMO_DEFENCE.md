# 答辩演示：自愈与记忆长轨迹

两个脚本都在项目根目录执行。执行前停留在首页“网络态势”，新事件约 2 秒内弹出并保留约 10 秒，点击后进入统一事件详情。演示生成的数据标记为 `controlled_test`，生产案件数量、处置率和长期收益统计只计算现场观测数据。

## 用例一：服务故障自愈

```bash
./scripts/demo_self_healing.py
```

脚本创建一个临时 systemd 服务，让它首次启动进入 `failed` 状态。随后调用系统正在使用的失败服务检测器、安全前置检查、`restart_unit` 白名单动作和结果观察器。验收条件包括：

1. 连续两次检测到同一故障，过滤部署瞬态。
2. 前置检查确认目标当前确实失败，动作范围只有一个服务。
3. 变更方案只包含一个 `restart_unit` 对应操作，一次性授权绑定方案摘要和目标。
4. 服务重启后进入 `active`，操作回执明确记录实际命令结果。
5. 观察窗持续读取服务及管理入口状态，最终轨迹写入 `resolved`。

事件详情用六段因果链展示检测、确认、调查、记忆、处置和回读。命令及原始记录收在折叠的“技术审计记录”。临时服务在脚本结束时删除，轨迹和验收回执保留。

## 用例二：记忆提速与长轨迹

```bash
./scripts/demo_memory_trajectory.py
```

脚本对同一个失败服务创建两起连续的受控案件：

1. 第一案关闭记忆检索，执行完整的服务故障检查并登记机器证据确认过的处理步骤。
2. 脚本从持久化接口读取第一案生成的唯一记忆标识，并核对来源会话。
3. 第二案开启记忆检索，系统根据相同资产、故障族和有效时间选中这个精确标识。
4. 当前状态再次确认服务失败后提前结束其余检查。
5. 页面显示候选检查数、实际执行数、节省检查数、记忆标识和轨迹活动数。
6. 案件页明确展示召回记录、来源调查、匹配原因、是否采用、两条检查路径及节省数量和时间。

页面主体显示六段因果链和记忆实际节省的检查数量；内部标识、命令和原始 JSON 位于折叠审计区。

演示与查看完成后统一清理：

```bash
./scripts/cleanup_demo_usecases.py
```

需要先核对删除数量时执行 `./scripts/cleanup_demo_usecases.py --dry-run`。清理目标只来自两个用例写入的 `controlled_test` 回执，执行期间网关会短暂停止并在清理后自动恢复。

## 答辩口径

- 自愈用例证明系统能从故障事实进入单服务动作，并用执行回执和多次现场回读确认恢复。
- 记忆用例证明第一案的具体记录实际改变了第二案的检查路径，收益由同一候选集合上的执行数量差值计算。
- 事件详情读取本案已保存轨迹，打开页面不会启动全量轨迹计算。
- `--test` 使用 1 秒间隔和 4 次回读，完整演示使用 2 秒间隔和 4 次回读。生产自愈服务继续使用原有观察策略。
