# 答辩演示：自愈与记忆长轨迹

两个脚本都在项目根目录执行。执行完成后打开首页“待处理事件”，首屏“答辩演示”会在 3 秒内刷新验收回执。演示生成的数据标记为 `controlled_test`，生产案件数量、处置率和长期收益统计只计算现场观测数据。

## 用例一：服务故障自愈

```bash
./scripts/demo_self_healing.py
```

脚本创建一个临时 systemd 服务，让它首次启动进入 `failed` 状态。随后调用系统正在使用的失败服务检测器、安全前置检查、`restart_unit` 白名单动作和结果观察器。验收条件包括：

1. 连续两次检测到同一故障，过滤部署瞬态。
2. 前置检查确认目标当前确实失败，动作范围只有一个服务。
3. 服务重启后进入 `active`。
4. 快速观察窗和稳定观察窗持续读取服务及管理入口状态。
5. 最终轨迹写入 `resolved`，页面显示实际回读次数。

页面点击“查看完整处置轨迹”，可查看检测、确认、命令、提交、采样和恢复记录。临时服务在脚本结束时删除，轨迹和验收回执保留。

## 用例二：记忆提速与长轨迹

```bash
./scripts/demo_memory_trajectory.py
```

脚本对同一个失败服务创建两起连续的受控案件：

1. 第一案关闭记忆检索，执行完整的服务故障检查并登记机器证据确认过的处理步骤。
2. 第二案开启记忆检索，系统根据相同资产、故障族和有效时间选中刚刚验证的步骤。
3. 当前状态再次确认服务失败后提前结束其余检查。
4. 页面显示候选检查数、实际执行数、节省检查数、记忆标识和轨迹活动数。
5. 案件页保留工作集、候选判断、原始证据、记忆介入结果和轨迹状态机提示。

页面点击“查看记忆效果与长轨迹”，会进入第二案。顶部案件流程条显示当前轨迹位置、历史同类下一步、重复状态占比和样本边界；案件主体显示记忆实际节省的检查数量。

## 答辩口径

- 自愈用例证明系统能从故障事实进入动作，并用多次现场回读确认恢复。
- 记忆用例证明历史记录实际改变了下一案的检查路径，收益由同一候选集合上的执行数量差值计算。
- 轨迹状态机当前用于可观测和人工排序，页面明确展示历史样本数与 `shadow_only` 模式。
- 自愈演示采用 2 秒快速观察窗和 3 秒稳定观察窗，便于现场演示。生产服务继续使用 60 秒快速观察窗和 180 秒稳定观察窗。
