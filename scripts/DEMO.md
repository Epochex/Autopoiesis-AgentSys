# 演示稿 · 感知 → 处置 → 验证

约 8 分钟。两个场景：一个系统自己修好，一个系统检测到了但**故意不动手**。
第二个比第一个值钱，因为它证明分级不是摆设。

访问地址 `http://192.168.1.27:2026`（nginx 监听 2026，反代到网关 127.0.0.1:8026）。

---

## 开演前 30 秒（可选，让时间线干净）

```bash
cd /data/Autopoiesis-AgentSys
./scripts/inject_incident.sh cleanup                       # 清掉上次的残留
rm -f /data/autopoiesis-runtime/sentinel-timeline.jsonl    # 清空历史，只留这次的链
systemctl restart netops-ops-console-backend               # 重启后哨兵自动跑起来
```

浏览器 **Ctrl+Shift+R 硬刷新**一次，停在「**态势**」页。

---

## 第一幕 · 注入真故障（30 秒）

```bash
./scripts/inject_incident.sh service-down
```

**边敲边说的话：**

> 这不是往数据库里插一条假告警。它真的创建了一个 systemd 服务、真的把主进程
> SIGKILL 掉，systemd 真的把它标成 failed。如果演示注入的是假数据，那只能证明
> 假数据是假的。

**然后什么都不用做**——哨兵每 15 秒自己巡一轮。

---

## 第二幕 · 告警自己找上门（约 30 秒）

**不用切页面。**就停在态势页，拓扑上方会自己冒出一条：

```
系统自己发现的   1 项处理中                    点一条看完整处置链路 ▸
刚发现   demo-collector.service   demo-collector.service 挂了。…   16:30:53
```

**这里要讲的：**

> 态势页原本画的是 FortiGate 历史语料，和实时巡检是两套数据。这一条是哨兵自己
> 发现的，直接顶在运维天天盯的那一页上——不然系统在后台把故障发现、修好、关掉，
> 屏幕上什么都不会变。

标签会自己往前走：`刚发现` → `处置中` → `已自愈`。

---

## 第三幕 · 点进去看完整链路（约 2 分钟）

**点那一行**，自动跳到「**长轨迹**」页，实时态势列表里对应的卡片已经选中。

顶部的环节条这时是**哨兵自愈循环**，不是 NetOps 那一条：

```
哨兵自愈循环   01 巡检发现  02 二次确认  03 前置校验  04 执行动作  05 观察期  06 回读验证
```

**这里最该讲的一句：**

> 这是两条不同的链路，所以画成两条轨道。哨兵根本没经过关联器和建议流，
> 如果复用 NetOps 那条轨道，就等于点亮了没跑过的环节。
> 亮着的环节是从时间线读出来的，不是写死的。

卡片右侧能看到：证据行、实测影响面、假设（这一族的置信度是 1.0，因为
探测器命中的是**实测状态**——服务就是 failed，不是推断出来的）。

---

## 第四幕 · 进剧场看影响范围（1 分钟）

卡片上点「**⧉ 全链路拓扑剧场**」。

剧场里是拓扑影响范围 + 左下角的**实时处置进度**，并排看：

```
系统正在处置  demo-collector.service                    [进行中]
● 发现 ─ ● 已确认 ─ ● 前置校验 ─ ● 执行 ─ ◉ 观察期 12次采样 ─ ○ 收尾
影响面   只影响 demo-collector.service 这一个服务，它现在是 failed
当前     改完回读通过，观察期内没有回归
```

**如果正好赶上观察期：**

> 采样数在往上跳，这 90 秒不是卡住了。改完了不等于修好了——状态可能在
> t+0 是对的、t+90 又掉了。接口起来又断、服务重启后二次崩溃、磁盘清完
> 又满，都是这样。所以要盯着。
>
> 这一段是我调研过 Dynatrace、Splunk、Cisco、ServiceNow 之后，发现四家全都
> 没有的：处置后观察期、自动回滚、误伤检测。它们的文档里只有"执行完了"，
> 没有"执行完之后我怎么知道没弄坏别的"。

---

## 第五幕 · 检测到但不动手（1 分钟）

**先等第一条链走完**（态势页那行变成「已自愈」）再敲：

```bash
./scripts/inject_incident.sh bruteforce
```

> 为什么要等：观察期里哨兵是阻塞的，那 90 秒不巡检。这期间注入的第二个故障
> 会推迟到观察期结束才被发现。这是真实行为，不是 bug，被追问就直说。

约 30 秒后态势页出现第二行，**琥珀色**，标着「只报不动」。点进去，环节条只亮到
`02 二次确认` 就断了——后面四级是暗的。

**这段是全场最该讲的：**

> 系统检测到了 12 次失败登录，但它选择不动手。封禁 IP 是可撤销的动作，
> 按理说可以自动做——但**封错来源就等于堵住自己的管理通道**。我人在家里
> 通过 Tailscale 连进来，系统把我封了，我就再也进不来了。
>
> 所以这一族的自动动作是空的。链条停在「无安全动作」是设计出来的，
> 不是没实现——环节条上后面四级不亮，就是它没跑过的证明。
>
> 一个演示里什么都自动修好了，恰恰藏起了更重要的一半。

## 收尾

```bash
./scripts/inject_incident.sh cleanup
```

## 可能被追问的三个问题

**「这些动作凭什么敢自动跑？」**
只有满足"目标已经在最差状态"的动作才自动：网卡已经没载波、服务已经 failed。
动它不可能比现在更差。碰防火墙、共享网段、还在服务的第三方设备的，一律只出
方案由人执行。

**「万一自动修反而把事情搞坏了？」**
五层：不可逆就不做 → 执行前算影响面 → 改完回读 → 观察期盯指标 → 自动回滚。
而且每个动作都挂了网关健康探针——**修好目标却把网关搞挂了，不算成功**，会判
`revert_unverified` 并要求人工介入。

**「重启会不会陷入死循环？」**
不会。连续两轮才动手；处置后进冷却直到恢复；重启前查 journal，如果是下游依赖
不通导致的崩溃，重启修不好，直接拒绝——**无限重启会把一次降级放大成一场故障**。

## 出问题时

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面还是旧的 | 浏览器缓存 | Ctrl+Shift+R |
| 态势页没有告警条 | 哨兵没开 | `tr '\0' '\n' < /proc/$(systemctl show netops-ops-console-backend -p MainPID --value)/environ \| grep SENTINEL` 应有 `=1` |
| 第二个故障迟迟不出现 | 前一条还在观察期 | 等它变「已自愈」再注入 |
| cleanup 后暴力破解那条还在 | journal 里那 12 条日志留在 10 分钟窗口内，会被重新检出 | 等 10 分钟，或演示时接受它一直在 |
| 不想等 | 手动推一轮 | `curl -X POST localhost:8026/api/rca/sentinel/poll` |
| 想看原始数据 | | `curl -s localhost:8026/api/rca/sentinel/timeline \| python3 -m json.tool` |
