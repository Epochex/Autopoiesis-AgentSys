# 网络调查记忆模块的业务目标与有效性测试

## 1. 业务目标

记忆模块服务于重复网络调查。它保存经过本轮证据核实的调查假设、探针顺序、资产画像和处置结果，在相似事件再次出现时参与上下文编译与探针排序。

业务收益只接受以下三类结果：

1. 在结论正确率持平或提高的条件下，减少探针、调查时长或人工升级。
2. 在现状变化、故障归属变化和无关历史出现时，维持正确结论并控制不必要动作。
3. 记忆影响动作选择时，保留审批、动作回执、结果回读和回退证据。

“记忆被检索”“记忆被写入”和“记忆数量增加”属于机制观测量。它们不能单独形成业务收益结论。

## 2. Agent 在内网态势感知中的位置

| 对象 | 输入 | 维护的状态 | 输出 |
|---|---|---|---|
| 态势事实层 | 告警、设备状态、配置、流量和工具回执 | 当前资产与事件事实 | 可引用的本轮证据 |
| 任务编排服务 | 调查目标、证据预算、权限、工具目录 | 已执行探针、失败探针、剩余预算和候选根因 | 下一探针、停止条件、升级材料或受控动作请求 |
| 记忆系统 | 已核实历史、当前查询、资产范围 | 记忆版本、置信度、冲突、衰减、隔离和归因 | 进入上下文编译的历史候选及来源标识 |
| 判断与核查 | 当前证据、候选根因、动作回读 | 证据覆盖与结论状态 | 已核实结论、未决项和记忆反馈 |

Agent 的工程意义集中在部分信息条件下的调查控制：依据已经看到的证据选择下一探针，在预算与权限边界内停止、升级或请求动作。固定规则能够稳定完成的案例保留为基线。记忆模块需要在相同工具、相同判断器和相同案例下超过关闭记忆或固定操作手册，才获得额外价值信用。

## 3. 记忆信用链

一次运行按以下链路记录信用：

1. 检索器返回候选记忆及分数。
2. 上下文编译器决定哪些候选进入本轮上下文。
3. 任务编排服务执行探针并记录新证据。
4. 判断器依据新证据形成根因与停止条件。
5. 归因账本记录实际影响探针或结论的记忆 ID。
6. 结果核查后，记忆获得强化、冲突、替换、衰减或隔离事件。

前端只展示这六类可追溯事实。业务价值需由真实时间序列案件的配对结果给出，页面文案和固定案例不代替这项证据。

## 4. 内部测试集

机器可读定义位于 `domains/network_rca/fixtures/memory_effectiveness_cases.json`。执行器复用真实的任务编排服务、上下文编译器、只读探针、判断器和记忆存储，位于 `core/eval/memory_effectiveness_suite.py`。

五个实验臂：

| 实验臂 | 含义 |
|---|---|
| M | 持续接收已核实反馈的相关记忆 |
| A0 | 不执行探针的空跑下界 |
| A1 | 相同组件与工具，关闭记忆 |
| A2 | 等条数、近似 token 体积的无关历史 |
| A3 | 固定且不随运行更新的人工操作手册 |

配对键为 `source_case_id + seed`，执行顺序在每个配对内按种子打乱。收益门槛预先写入测试集：配对成功率使用 McNemar mid-p，探针数使用 Wilcoxon 配对检验，显著性门槛为 0.05。

## 5. 正反用例

| 用例 | 希望看到的行为 | Bad use case | 当前状态 |
|---|---|---|---|
| 重复故障 | 保持核实成功率并减少探针 | 存储和上下文持续增长，探针与正确率没有改善 | 现场复发对从 3 步降至 1 步，根因与决定性探针一致 |
| 无关历史 | 等量无关记忆不改变根因与动作 | 无关历史改变根因、引用或动作 | 当前留出集未观察到伤害 |
| 当前已恢复 | 新探针显示健康后保持观察 | 沿用历史故障并请求修改 | 当前信号门已覆盖，成功动作另有稳定回读 |
| 故障归属变化 | 停止本地修改并生成升级材料 | 历史处置越过当前所有权边界 | 当前信号门已覆盖，越权动作由资格检查拒绝 |
| 固定手册基线 | 动态记忆降低调查成本 | 维护成本增加，结果与固定手册一致 | 三次中位数减少 5 个探针、2 个确认步骤和 2695.927ms |
| 上下文成本 | 新增 token 由探针、时长或成功率收益覆盖 | 接近全库检索，业务指标保持原值 | 公开 542 对中 539 对弃权，现场配对无额外越域上下文 |
| 根因冲突 | 新证据推翻旧根因后停止给旧记忆信用 | 旧根因持续获得强化 | 记忆操作单测已覆盖，完整回放待补 |
| 授权动作回读 | 审批、回执、回读、回退形成闭环 | 调查结论正确，动作缺少授权或结果回读 | 现场 5/5 取得终态回读，覆盖成功恢复与失败停止 |

## 6. 业务准入数据

固定 seed 和固定标签用例只锁定评分器、检索器和状态边界，结果不进入项目完成度。业务准入使用 `core/eval/temporal_case_evaluation.py` 读取真实案件导出轨迹，分开计算稳定根因率、过早关闭率、反证修正率、检查点恢复率、重复探针和达到稳定根因的步数。

当前业务链已经把实时事件、检索、现场证据、假设变化、动作回读和结案决定接入持久化案件。2026-08-31 受控现场运行 `20260831T115350Z-d03425` 保存了一个首次事故与复发事故的独立案件对，并对复发故障分别执行固定脚本、关闭记忆和完整系统，每个策略重复三次。三臂确认同一根因；完整系统中位数从 6 个探针和第 3 步确认降至 1 个探针和第 1 步确认。这个样本证明机制与收益链可以实际执行。跨天生产复发仍需持续累积，以估计收益分布和长期稳定性。

公开 RCAEval 提供更大规模的负迁移检查：542 个历史对中，严格准入门只允许 3 对记忆介入，3 对均减少候选，0 对受损，539 对弃权。repetition 4 及以后组成的 159 对留出集保持 3 对改善、0 对受损。公开指标衡量候选排序，现场配对衡量真实探针数、首次确认步骤和墙钟时间，两者分别保留。

## 7. 公开 benchmark 对接

公开测试集分别覆盖记忆能力与 IT 任务结果，当前没有一个测试集同时覆盖本项目的跨事件记忆、内网设备调查、权限边界、动作回读和负迁移。因此采用分层对接：

| 层级 | 基准 | 用途 | 对接方式 |
|---|---|---|---|
| 记忆检索 | [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 多会话信息提取、时间推理、知识更新和拒答 | 保留现有 recall@5 外部锚点 |
| 轨迹记忆 | [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2) | 长轨迹中的状态、流程、环境陷阱和前提意识 | 下一阶段优先增加适配器，输出题型分解结果 |
| 记忆边界 | [MemoryAgentBench](https://arxiv.org/abs/2507.05257) | 检索、测试时学习、长程理解和选择性遗忘 | 用于根因冲突、失效经验和选择性隔离 |
| 跨回合执行 | [EvoMemBench](https://github.com/DSAIL-Memory/EvoMemBench) | 跨 episode 的知识与执行经验迁移 | 检查记忆是否改变后续执行结果 |
| 企业 IT 任务 | [ITBench](https://github.com/itbench-hub/ITBench) | SRE、CISO 和 FinOps 的可验证任务 | 对同族故障执行无记忆与有记忆配对 |
| 可注入故障环境 | [AIOpsLab](https://github.com/microsoft/AIOpsLab) | 部署微服务、注入故障、导出遥测并交互评测 | 用于动作、回读和恢复结果测试 |

当前接入状态：

1. 内部固定案例用于 CI 契约，不进入业务通过数。
2. RCAEval 全量 733 案例与 542 个复发对用于候选召回、结论门和负迁移测试。
3. ITBench-Lite 的 35 个 SRE 场景用于自动范围与 Kubernetes 事件召回测试。
4. AIOpsLab 的 89 个任务和 35 个注入恢复文件作为外部能力清单；本项目动作结果由本机回环故障验收独立计分。
5. LongMemEval-V2、MemoryAgentBench 和 EvoMemBench 保留为长程状态、冲突遗忘和跨 episode 扩展项，不计入当前六项通过数。

## 8. 面试表达

> 我把记忆模块定义为重复网络调查的成本优化器，并对历史先验的负迁移进行独立评测。每轮重新采集当前设备证据；被上下文编译器纳入、实际改变探针顺序，并由当前决定性探针再次确认的记忆才获得信用。公开 542 个复发对中，严格准入门只介入 3 对，改善 3 对、伤害 0；现场同一故障的三臂配对中，完整系统把首次确认从第 3 步缩短到第 1 步，并减少 5 个探针。动作后的原系统回读决定结案或停止继续变更。

当被追问“KV 或规则能否完成”时，直接展示关闭记忆与固定脚本两条基线：三种策略使用相同故障、相同工具目录和相同判断条件，完整系统保持根因一致，并减少探针、确认步骤和中位耗时。下一项工程任务是持续积累跨天生产复发，检验当前小样本收益能否保持。
